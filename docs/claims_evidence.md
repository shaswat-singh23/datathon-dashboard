# Claims & Evidence appendix

One row per claim that appears in the README or on a dashboard page. Each row names the table or query behind the number, the result, the alternative explanation that was tested, the main limitation, the `findings/` file that holds the full reproduction, and the check status recorded for that claim.

**Status gate.** Team rule (AGENTS.md, `findings/README.md`): a number goes into slides, the video or the write-up only from a finding whose `Checked by` is not `unchecked`. Read each claim's `Checked by` cell together with the linked finding: a check may cover only specific claims within a finding. Named checks apply only to that scope; an `unchecked` claim still needs an independent check before it can be cited in the story. Whether an agent re-run counts as a check remains the decider's call; a named tool-assisted check does not establish a human re-run. A reviewer who re-runs a claim and reproduces its numbers records their name, tool, date and checked scope in the finding and updates the corresponding appendix cells. If the two records disagree or the scope is unclear, resolve that before citing the claim.

Conventions used throughout: Jan 1 to Jun 30 2025 unless stated; money math through `royale/money.py` (ratios are ratios of sums, theo = coin-in × (1 − configured RTP), luck = house win − theo); comparisons per available hour; 1,018 off-floor `machine_day` rows (`location_id` null) excluded from machine comparisons; location from `placements` at gaming-day start. Pages read only committed marts in `marts/`; the Reproduce blocks need the organizer data through `DATA_DIR`.

## How to check a row

1. Point `DATA_DIR` at a verified organizer clone (row 17).
2. Open the finding, run its Reproduce block from the repository root, and compare every number quoted here.
3. If they match, change the finding's `Checked by` line to your name in a PR, then update the matching row's last column here. If they do not match, open a `bug` ticket naming the row.
